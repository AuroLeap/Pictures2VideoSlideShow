# User Needs (UN-###)

Owned by the [End User persona](../../.claude/agents/end-user.md). Plain-language needs and edge-case expectations inferred from the [README](../../README.md). Engineering translations live in [system-requirements.csv](system-requirements.csv) (referenced by `UN-Refs`); do not restate them here. See [process.md](../process.md) for the ID/anti-duplication rules.

Priority: **M** = Must · **S** = Should · **C** = Could.

I am a non-programmer hobbyist on Windows. I point the tool at a folder of photos and videos and expect looping slideshow MP4s that *just play* on my cheap digital picture frame. I care most about: getting set up without a fight, not having to babysit a long run, and the tool behaving sanely when something goes wrong. I should not have to read source code to use this.

## Edge-case expectations

How the system should behave when things go wrong. This is the part I care about most — a frame project runs for a long time unattended, so failures must be safe, visible, and recoverable. Each row is a user-facing expectation; the System Engineer turns it into measurable SRs.

| UN-ID | Scenario | Expected behavior |
|---|---|---|
| UN-013 | **Power loss / process killed mid-run** | No corruption of my *source* media (inputs are only ever read, never modified in place). A killed run leaves no half-written file masquerading as a finished output — partial/temp output is clearly distinguishable from a complete MP4 (and ideally cleaned up or resumable). Re-running after a crash is safe and does not silently skip or double-produce content. |
| UN-014 | **Application failure / FFmpeg error or FFmpeg missing** | The tool fails loudly with a plain-language message naming the cause (e.g. "FFmpeg not found on PATH", "FFmpeg exited with an error on file X"), a non-zero exit status, and a hint at the fix. It does not hang indefinitely or report success when no valid output was produced. |
| UN-015 | **Corrupt / unreadable / unsupported input media** | One bad file does not abort the whole run by default. The tool skips it, names the skipped file and why, continues with the rest, and reports the count of skipped items in the final summary so I can decide whether to re-source them. |
| UN-016 | **Storage full / no space for output or temp** | The tool detects it can't write, stops with a clear "out of disk space"/"cannot write to <path>" message, and does not leave a truncated file that looks complete. It fails the run rather than producing an unusable output silently. |
| UN-017 | **Output device / SD card / network path removed or unwritable mid- or pre-run** | If the output (or input NAS) path is missing or becomes unwritable, the tool reports the specific path and the problem and stops cleanly, rather than crashing cryptically or silently writing nowhere. Removing the card after a file is fully written never corrupts already-completed outputs. |
| UN-018 | **Output too big for the target frame / FAT32** | Covered as a *pre-run* protection in UN-006; as an edge case, if an output still ends up oversized the tool surfaces it in the summary (file path + size) rather than letting me discover it only when the frame rejects the card. |
